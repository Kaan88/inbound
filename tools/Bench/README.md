# tools/Bench: the PERF.8 baseline

An end-to-end benchmark console program (plain `net10.0`, runs on Linux and Windows). It takes the baseline asked for in
`docs/plans/performance-areas.md` ("Benchmarking, and whether to try Rust" → "Baseline to take") as stage A2 of
`docs/plans/sites-and-performance-order.md`. It changes nothing under `src/`: it uses the public APIs of `DownloadManager.Engine`
and `DownloadManager.Persistence` and the shipped programs.

It is not BenchmarkDotNet on purpose: the runs are long and end to end.

## Running it

Linux (publishes the three programs self-contained, builds the tool, runs everything):

```bash
scripts/perf-bench.sh --out artifacts/perf-bench/linux-pc            # full baseline (15 to 30 minutes)
scripts/perf-bench.sh --out artifacts/perf-bench/smoke --quick       # smoke test, a minute or two
```

Windows:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\perf-bench.ps1 -Out artifacts\perf-bench\windows-pc
powershell -ExecutionPolicy Bypass -File scripts\perf-bench.ps1 -Out artifacts\perf-bench\smoke -Quick
```

Both end in the same command (`Bench all --out DIR --cli X --native-host X --host X ...`); `dotnet build tools/Bench -c Release`
then `dotnet tools/Bench/bin/Release/net10.0/Bench.dll all --out DIR ...` does it by hand. A part can be run alone
(`throughput`, `saves`, `start`); `start` needs the three program paths, the others need nothing published.

For the baseline: a quiet machine, power plan or governor fixed to the one you will use later (note it with `--note`), a
`--disk-dir` on the real SSD that has at least 20 GB free, nothing else running. Use the same options on both machines.

### Options

| option | default | meaning |
| --- | --- | --- |
| `--out DIR` | required | CSV files and `summary.md` go here |
| `--quick` | off | 64 MiB files, 1 repeat, 10 saves, 3 start runs; for smoke tests only |
| `--disk-dir DIR` | `<out>/work-disk` (the scripts: `artifacts/bench-work`) | destination and state folder for "disk" runs. The tool warns if it is on tmpfs/ramfs |
| `--ram-dir DIR` | Linux: `/dev/shm`; Windows: none (RAM rows are skipped) | RAM-backed destination folder |
| `--size N\|auto` | `auto` (quick: `64M`) | file size (`512M`, `8G`, bytes). `auto` probes 256 MiB first and sizes the file for `--target-seconds` |
| `--target-seconds` | 30 | what `auto` aims for |
| `--max-size` / `--ram-max-size` | 16G / 4G | caps for `auto` (also capped by 60 % / 40 % of the free space) |
| `--segments` | `1,8,16` | segment counts (the job's requested connections) |
| `--host-limits` | `8,16` | the engine's per-host connection limit; see "16 segments" below |
| `--repeat` | 3 (quick: 1) | runs of every throughput configuration |
| `--server` | `auto` (= `static`) | `static` or `testserver` for the engine runs |
| `--ceiling-size` | 4G (quick: 64M) | bytes read per server-ceiling measurement |
| `--save-count` | 300 (quick: 10) | saves per record, variant and folder |
| `--start-runs` | 10 (quick: 3) | measured runs per start scenario |
| `--cli`, `--native-host`, `--host` | none | published programs for the start times; without them that part is skipped |
| `--note TEXT` | | free text written into `environment.csv` |

## Output files

All values use the invariant culture. MB = 10^6 bytes, GB = 10^9 bytes, MiB = 2^20. CPU seconds are this process's user + kernel
time. Column sets are stable; a column is added only at the end of a file.

### `environment.csv` (`key,value`)

OS, runtime, CPU model and governor (Linux), logical CPUs, memory, load average at start, and the file system type of the disk
and RAM folders (`ext4`, `tmpfs`, `NTFS/Fixed`).

### `ceilings.csv`: can the server keep up?

`server, method, connections, size_bytes, seconds, mb_per_s, client_cpu_s`

Raw read-and-discard from each server, with no engine and no disk, by a client in the bench process (`httpclient`: N parallel range
requests, 128 KiB reads) and by `curl -o /dev/null` (`curl`, 1 connection; skipped if curl is missing). Servers: `static` (this
tool's Kestrel file server) and `testserver` (`tools/TestServer`, `/file/` endpoint, 512 MiB at most). If the engine's MB/s is
anywhere near the server's ceiling, the server is the limit and the engine number says little.

Why the static server is used for the engine runs: the TestServer keeps the whole file in one `byte[]` (size is an `int`, 2 GiB at
most, generated byte by byte on first request) and its `/large/` endpoint has no range support, so it cannot give 30 s runs at
gigabyte speeds with segments. The static server serves slices of one shared 1 MiB block, allocates nothing per request and
supports `Range`. Both ceilings are written so that the reader can see it.

### `throughput.csv`: one row per engine run

`run_id, utc, server, dest_kind, filesystem, segments, host_connection_limit, repeat, size_bytes, bytes_written, wall_s, mb_per_s,
cpu_user_s, cpu_kernel_s, cpu_total_s, cpu_s_per_gb, alloc_bytes, alloc_bytes_per_gb, gc0, gc1, gc2, peak_working_set_bytes,
server_cpu_s, progress_callbacks, max_active_connections, job_saves, checkpoint_saves, verified, reached_target_seconds, result`

| column | meaning |
| --- | --- |
| `dest_kind`, `filesystem` | `disk` or `ram`, and the file system of that folder |
| `segments` | the job's `RequestedConnections` |
| `host_connection_limit` | the engine's per-host limit (`UpdateHostConnectionLimit`), as the Host sets it from Options |
| `bytes_written`, `wall_s`, `mb_per_s` | what the engine reported written, wall time from just before `ExecuteAsync` to its result, and their quotient |
| `cpu_*` | this process's CPU time over that window; `cpu_s_per_gb` = `cpu_total_s` / GB written. The server runs in another process, its CPU is `server_cpu_s` and is not included |
| `alloc_bytes(_per_gb)` | `GC.GetTotalAllocatedBytes(precise: true)` difference over the window (everything in the process, including the progress callback and the saves) |
| `gc0/1/2` | `GC.CollectionCount` differences |
| `peak_working_set_bytes` | highest working set seen by a 200 ms sampler during the run (the process-wide `PeakWorkingSet64` is not per run) |
| `progress_callbacks` | how often the engine reported progress |
| `max_active_connections` | highest `ActiveConnections` the engine reported: proof of how many connections really ran |
| `job_saves`, `checkpoint_saves` | the 5 s job-file saves of the Host's progress callback, and the engine's own checkpoint saves; both are in the CPU and allocation numbers |
| `verified` | the downloaded file's first, middle and last 4 KiB match the server's pattern (static server only) |
| `reached_target_seconds` | wall time reached `--target-seconds`. `false` is expected in `--quick` and for RAM folders, which cannot hold a 30 s file at gigabyte speeds |
| `result` | `ok` or the failure |

How the engine is run: in this process, as the Host does (`DownloadManager.Host/Program.cs`, `Host.Linux/Program.cs`): the same
`EngineOptions`, the real `JsonCheckpointStore` (the engine saves a checkpoint and flushes the part file every 5 s) and a progress
callback shaped like `DownloadManagerService`'s: it updates the job under a lock, makes a snapshot object at most every 300 ms
(a `Clone()` stands in for `Map(job)`, which is internal to the Runtime) and saves the job with the real `JsonJobStore` every 5 s.
The part file is `<final>.<jobId>.part` in the destination folder as in production. State files (jobs, checkpoints) always live
under `--disk-dir`, also for the RAM runs.

**16 segments and the host limit.** The engine limits connections to one host (`MaxConnectionsPerHost`, Options default 8). A job
with 16 segments and the default limit therefore runs 8 connections at a time; `max_active_connections` shows it. The default
`--host-limits 8,16` runs the 16-segment configuration at both limits (other segment counts are not repeated, since the limit
changes nothing for them).

### `saves.csv`: what the saves cost

`record, segments, dir_kind, filesystem, variant, count, bytes_per_save, mean_ms, p50_ms, p95_ms, max_ms, writes_per_s, note`

`segments` is 0 for the job records. `record` is `job-plain` (a typed URL), `job-browser` (referrer, user agent and a cookie header, which the store seals) or
`checkpoint` with `segments` 1, 8 or 16. Saves are sequential (production writes one job's files one after another);
`writes_per_s` = `count` / total time. A few warm-up saves are not counted. `bytes_per_save` is the file size on disk, which answers
the JSON size question; the indented JSON is the product's current format.

| `variant` | what it is |
| --- | --- |
| `product` | the real `JsonJobStore.SaveAsync` / `JsonCheckpointStore.SaveAsync` |
| `replica-fsync` | a copy of `AtomicFile.WriteBytesAsync` (temp file, `WriteThrough`, `Flush(flushToDisk: true)`, rename) writing the same bytes. Should match `product` apart from serialisation and cloning |
| `replica-writethrough-only` | the same without the fsync |
| `replica-no-durability` | without write-through and without fsync (ordinary buffered write plus rename) |
| `serialize-indented`, `serialize-compact` | in memory only, `dir_kind` is `memory`; compact bytes are the real file's JSON without whitespace |

Write-through and fsync are hard-coded in the internal `AtomicFile` (`src/DownloadManager.Persistence/JsonStores.cs`) and cannot be
switched through any public API. The `replica-*` rows are therefore a copy of that routine inside the bench, not product code.

### `starts.csv`: start times

`target, scenario, kind, run, first_output_ms, ready_ms, exit_ms`

Run 0 of every scenario is a warm-up (`kind` = `warmup`) and is left out of the statistics; `summary.md` gives median, min and
max of the measured runs. Times are milliseconds from just before `Process.Start`.

| target / scenario | first_output_ms | ready_ms | exit_ms |
| --- | --- | --- | --- |
| `cli` `--version`, `--help`, `doctor --no-start` (no Host) | first byte on stdout/stderr | | process end |
| `cli` `status --no-start` (Host running) | first byte | | process end |
| `native-host` first reply to `host.ping` | first byte on stdout | the ping's reply frame arrived | after closing stdin, process end |
| `host` endpoint accepts connection | | the isolated Host's socket (Linux) or pipe (Windows) accepts a connection | from the `host shutdown` command to the Host's exit |

The native host is started the way a browser does (the trusted extension origin as its argument) against a running isolated Host
and sent one `host.ping`. The Host is started with `--background` in a fresh data folder each run.

**Isolation.** Every start scenario gets its own `DOWNLOADMANAGER_INSTANCE` (`bench-<random>`) and `DOWNLOADMANAGER_DATA` (a folder under
`--disk-dir`), so the endpoint name differs from the real one (the tool checks this and refuses otherwise), and the folders are
deleted afterwards. On Linux the child's `XDG_RUNTIME_DIR` (sockets), `XDG_CONFIG_HOME` and `XDG_DATA_HOME` point into temp folders
and `DBUS_SESSION_BUS_ADDRESS` is removed, so the Host cannot reach the desktop keyring, tray or notifications. The consequence: **the
Linux Host number leaves out the keyring, tray and notification set-up a real start does**, and the Host keeps its secret key in a
file in the data folder. The Host is stopped with the CLI's `host shutdown` against the same instance.

### `summary.md`

All of the above in tables, plus a "Noise" section with the load average before and after and every warning (a "disk" folder on
tmpfs, a run shorter than the target, a failed run).

## What each number is good for

- `cpu_s_per_gb` and `alloc_bytes_per_gb` are the figures PERF.9 changes (read timeout per read, pooled buffers, larger writes). The
  engine is worth a Rust comparison (PERF.14) only if it uses a large share of a core at speeds that matter.
- RAM against disk runs separate the engine from the disk. State files are written to `--disk-dir` in both.
- `saves.csv` shows what the 5 s saves cost and how much of it is fsync (PERF.12) or JSON size.
- `starts.csv` is the before-figure for ReadyToRun (PERF.11) and Native AOT (PERF.10).

## Known noise

- CPU frequency governor and boost: set `performance` (Linux) or the High performance plan (Windows) and say which in `--note`.
- Other load: the machine's other processes and a busy disk change every number. Check `loadavg` in `summary.md`; rerun if it is not low.
- Page cache: disk runs go through the OS cache (the engine flushes every 5 s); the 2nd and later repeats can be faster. Use `--repeat`
  and look at the spread, not a single run. An almost full SSD is slower.
- Antivirus (Windows): exclude `--disk-dir` or note that it was on.
- Short RAM runs: a RAM folder cannot hold 30 s of gigabyte-speed data, so `reached_target_seconds` is `false` there; the CPU and
  allocation per GB are still meaningful.
- Start times: the first run after a build is cold (the warm-up run shows it); published builds only, not `dotnet run`.
- The progress callback's snapshot is a `Clone()`, not `Map()`: allocations per GB are close to production but not identical.
- The `static` server is a loopback server on the same machine: it uses CPU on the same cores as the engine, in another process.
